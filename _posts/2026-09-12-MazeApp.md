Years ago, in school, I invented (or perhaps re-invented) a type of graph paper maze which I have been obsessed with ever since. It flips the logic of mazes on its head: instead of choosing your turns freely, you can only turn when you hit an obstacle — otherwise you're forced to walk in a straight line until something stops you. What I produced was a type of *ricochet* maze. Now, in 2026, I have built a web version of this maze using Claude Code, which you can play [here](https://ricochet-maze.netlify.app/?tutorial).
<!--end_summary-->

This web project began in 2017. At that time, I had a budding interest in coding, so I built a working computerized version of the maze as a web page in vanilla JavaScript, complete with an auto-solver feature. It worked well, but the interface was little more than unstyled buttons with plain text on a white background. So in 2026, I used Claude Code to rework the UI from the ground up. The result is mobile-friendly, colorful, and satisfying to play.

As an experiment, while I was vibe coding a new user interface, I had Claude Code produce one of the mazes (Easy Maze 1). I gave it a simple prompt: build a maze from scratch, comparable to the others already on the site. It spun on the request for what felt like ten to twenty minutes before producing a functional result — a novel XML file format I'd invented myself, translated by an AI that had never seen it before. I pushed it further, asking a few times for more obstacles and paths to raise the difficulty. Each time, it added a little, but never much; the final solved path is, quite literally, just up-right-up-right-right. When I suggested it try working in a left turn somewhere, it didn't take the hint. My best guess is that this task was unusually hard for a language model: it's one thing to generate an image, but reasoning about space and paths in an obscure text format is a different kind of problem, one that LLMs may have difficulty with. Whatever the cause, one strength did stand out — the output file was thoroughly documented, with comments tracing Claude's thought process throughout. You can see this novel maze file <a href="/resources/easy1.maze.txt" target="_blank">here</a>, or play the maze itself [here](https://ricochet-maze.netlify.app/?maze=easy1.maze). It's a fitting test case, since that invented format traces straight back to the paper mazes I started drawing as a kid.

Part of the inspiration, from what I remember, was visiting what I think may have been George Washington's Mount Vernon in the early 2000's. I remember seeing in the Pioneer Farm a small ricochet maze constructed from short hay bales. In this maze, you were allowed to turn only when you hit a wall; otherwise, you had to walk straight. My memory is a bit fuzzy; it seems unusual that there would have been a maze at this location, but this is what I remember. I was a kid. The maze was somewhere.

This same rule works just as well on graph paper: draw a start, an end, and a scattering of obstacles, and the path only turns where it hits one. Because so few walls are needed to define a path, a finished ricochet maze looks almost empty compared to a traditional maze — mostly straight lines with just enough obstacles to redirect them. That sparseness is what makes them hard to solve: there's no wall to trace with your hand, no dead end to back out of, just a long line that could bend anywhere between where you are and the exit.

That's the strange pleasure of a ricochet maze: you're never quite sure how close you are to the end, because the path can go anywhere until it doesn't. I've spent more hours than I'd like to admit lost in these things, on paper and now on screen, and I hope this version gives you the same itch to keep going. If you get stuck, try working backwards from the exit — and the auto-solver is always there if you'd rather just see how it's done.
